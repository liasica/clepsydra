# Clepsydra 系统设计

> 日期：2026-08-04
> 状态：待用户审查

## 一、背景与目标

Clepsydra 是统计兼职工作量（人天）并完成月度对账的内部系统，服务于乙方（超级管理员）与甲方（需求方）之间的技术服务合作。

合同依据（《极光出行系统技术服务合作协议》）中影响系统设计的硬规则：

- 附加开发费 1200 元/工作日，1 工作日 = 8 小时，实际一天工作可折算多个人天
- 最小计费单位 0.5 个工作日，同一自然月累计汇总结算
- 每月 10 日前向甲方提交上月费用对账单，与基础维护费 12000 元/月统一结算
- 需求须先书面确认范围、预计工时；交付后甲方限期验收，逾期视为通过
- 同一工单缺陷批次累计不超过 1 人天的，乙方可自主减免费用

重要定位：本系统即合同第十条第 5 款认可的「项目管理系统」，需求确认、工时确认、账单确认的操作记录具有书面确认的合同效力，因此**审计日志是核心需求而非可选项**。

## 二、已确认的关键决策

1. 账单为完整费用对账单：人天 + 金额（单价快照）+ 基础维护费
2. 需求方**仅登录确认**，不做免登录分享链接
3. 确认窗口口径**可配置**：自然日（默认）或工作日
4. 跨月边界采用**出账前锁定**：生成上月账单时，将上月完成且未确认的需求全部自动确认
5. 后端 Go + ent + PostgreSQL；前端 Vue3（vue-starter 初始化）
6. 账单每月自动生成草稿、**手动分享**；本期不做外部推送通知（邮件/微信），service 层预留 Notifier 接口
7. **仅参考 nexa 的目录结构**，不引入 `nexis.run/nexa` 依赖，**不使用 DI 框架**，`main.go` 手写构造函数装配
8. 日志用 zerolog + lumberjack：每日轮转（cron 每日 00:00 调用 `Rotate()`）、保留 30 天、单文件上限 100MB、gzip 归档

## 三、架构与技术栈

| 用途 | 选型 |
|---|---|
| HTTP 框架 | echo v4 |
| ORM | ent（PostgreSQL） |
| 配置 | viper（YAML + 环境变量） |
| 日志 | zerolog + lumberjack |
| 定时任务 | robfig/cron v3（幂等扫描式） |
| 认证 | golang-jwt v5 + bcrypt |
| 前端 | Vue3 + Vite + TypeScript（vue-starter） |

目录结构（参考 nexa 的 cmd/internal 分层）：

```
clepsydra/
├── cmd/clepsydra/main.go     # 入口 + 手动装配
├── internal/
│   ├── config/               # 配置加载
│   ├── ent/schema/           # ent schema
│   ├── dao/                  # 数据访问层
│   ├── service/              # 业务逻辑（含 Notifier 预留接口）
│   ├── api/                  # handler / router / 中间件
│   ├── task/                 # 定时任务：自动确认扫描、账单生成
│   └── workday/              # 节假日与工作日计算（纯函数包）
├── dashboard/                # Vue3 前端
├── config.yaml
├── .golangci.yml
└── Makefile
```

依赖方向自上而下：`api / task → service → dao → ent`；`workday`、`config` 为底层公共包，禁止反向依赖。

定时任务：

- 每日 00:00 — 日志轮转
- 每日 00:05 — 扫描过期未确认的需求与账单，执行自动确认
- 每月 1 日 00:10 — 出账前锁定 + 生成上月账单草稿
- 服务启动时自检：上月账单不存在则补生成（宕机漏跑兜底）

节假日数据：内置年度节假日/调休 JSON 导入 Holiday 表，设置中心可查看维护，不依赖外部 API。

## 四、领域模型

### 实体

- **User**：用户名、密码（bcrypt）、姓名、角色（admin 超级管理员 / client 需求方）、启用状态；需求方可多账号
- **Demand（需求/项目）**：标题、描述、预估人天、人天确认信息（确认人/时间/是否自动）、预测开工日期、实际开工日期、实际完成日期、实际人天、状态、确认截止时间（`accept_deadline`）
- **Bill（账单）**：账期（YYYY-MM，唯一）、状态、单价快照、基础维护费快照、合计人天、合计金额、分享时间、确认截止时间、确认信息（确认人/时间/是否自动）
- **BillItem（账单明细）**：所属账单、关联需求、需求状态快照、人天、金额、是否减免、备注
- **Setting**：kv 存储（见下方设置项清单）
- **AuditLog**：操作人、动作、目标类型/ID、详情（JSON）、时间；只增不改不删
- **Holiday**：日期、类型（holiday 节假日 / workday 调休补班日）

### 人天存储

人天一律用整数「半天数」存储（1 人天 = 2，0.5 人天 = 1），杜绝浮点误差，展示层换算。

### Demand 状态机

```
draft（草稿）→ pending_estimate（待确认人天）→ confirmed（已确认待开工）
→ in_progress（进行中）→ pending_acceptance（完成待确认）→ accepted（已确认）
```

- 流转白名单在 service 层校验，非法流转拒绝
- `pending_estimate → confirmed` 由需求方确认，**无自动确认**（开工前无时限压力）
- `pending_acceptance → accepted` 由需求方确认或系统自动确认（见业务流程）

### Bill 状态机

```
draft（草稿）→ pending（已分享待确认）→ confirmed（已确认）
```

- 草稿可重新生成、可调整减免；已分享未确认可撤回到草稿重发（记审计）
- 已确认账单永久锁定，不可变更

### 设置项清单

| key | 默认值 | 说明 |
|---|---|---|
| `bill_include_statuses` | accepted, in_progress, confirmed | 账单包含的需求状态范围 |
| `demand_confirm_window` | 5 | 需求完成确认窗口（天） |
| `bill_confirm_window` | 3 | 账单确认窗口（天） |
| `window_unit` | natural | 窗口口径：natural 自然日 / workday 工作日 |
| `daily_rate` | 1200 | 人天单价（元），生成账单时快照 |
| `base_fee` | 12000 | 每月基础维护费（元），生成账单时快照 |
| `saturday_as_workday` | true | 周六是否算工作日 |

## 五、核心业务流程

### 1. 工作日与出账日计算（workday 包）

- **工作日定义**：非节假日，且属于周一至周六（`saturday_as_workday` 默认 true），或为调休补班日（周日补班也算工作日）
- **出账截止日**：默认每月 10 号；若 10 号非工作日，从 10 号起逐日往前找，取第一个工作日（即 1–10 号中离 10 号最近的工作日）；仅用于站内提醒，不强制阻断
- **窗口截止**：`deadline(起点, N, 口径)` 统一函数——自然日直接 +N 天；工作日口径逐日跳过非工作日累计 N 天。需求确认与账单确认共用

### 2. 需求完成确认流

1. 管理员标记完成：填实际开工/完成日期、实际人天 → 状态转 `pending_acceptance`，落库 `accept_deadline`
2. 需求方登录确认 → `accepted`（记录确认人与时间）
3. 每日 00:05 扫描：`now > accept_deadline` 且仍未确认 → 自动 `accepted`（审计标记「自动确认」）
4. 出账前锁定：每月 1 日生成上月账单前，凡实际完成日期在上月且仍为 `pending_acceptance` 的需求一律自动确认（审计标记「出账锁定」）

### 3. 账单流

1. 每月 1 日 00:10 自动生成上月账单草稿（账期唯一约束防重）
2. 明细按 `bill_include_statuses` 抓取，分两类行：
   - **计费行**：账期内完成且已确认（accepted）的需求 → 金额 = 人天 × 单价快照；行级减免开关，减免后金额为 0、人天仍展示
   - **展示行**：进行中（in_progress）/ 已确认未开工（confirmed）→ 只列预估人天与预期开始日期，不计费；展示行仅为信息披露，同一需求完成后在其完成月的账单中转为计费行，不会重复计费
3. 账单合计 = Σ 计费行金额 + 基础维护费快照
4. 管理员检查草稿（可调减免、可重新生成）→ 点「分享」→ `pending`，落库 `confirm_deadline`；线下通知需求方登录确认
5. 需求方确认 → `confirmed`；每日扫描逾期自动确认
6. 首页待办提醒：出账截止日当天账单未分享、存在待确认需求/账单等

### 4. 错误处理与并发

- 定时任务全部幂等扫描式：判断条件基于数据状态，重复执行结果一致，漏跑次日自动补
- 确认操作用条件更新（`UPDATE ... WHERE status = ...`）防重复确认
- API 统一错误响应结构，业务错误码与 HTTP 状态分离
- 所有确认/流转/减免操作写 AuditLog
